# u3 — Executor agent: use git worktree instead of shared working tree

## Goal

Update `agents/reagent-executor.md` so EXECUTE jobs use `git worktree add` at the bridge-assigned `worktreePath` instead of `cd repoPath && git checkout <branch>`. Each concurrent executor gets its own isolated working tree with a dedicated index, eliminating the `.git/index.lock` races and branch-collision bugs identified in the diagnosis.

## Scope

- `agents/reagent-executor.md`

## Approach

### Context

The executor agent is a markdown prompt file with a YAML frontmatter header and a natural-language procedure. The current procedure step 1 reads:

> `cd` to `repoPath`. Create/switch to the `branch` you were given.

This races when two executors run concurrently — both `git checkout` into the same working tree.

### Changes to make

The executor is now also given a `worktreePath` argument (the bridge stores it on the `WorkItem` and the orchestrating pipeline skill passes it through). Update the agent document in three places:

**1. Header description line (line 3) and the inputs paragraph (line 8):**

Extend the list of given inputs to include `worktreePath` (e.g. `~/.reagent/worktrees/<id>`). The updated inputs sentence should read:

> You are given: a work item `id`, a target `repoPath`, an approved `plan` (diagnosis + direction), a `branch` name (e.g. `reagent/<slug>`), a `worktreePath` (e.g. `~/.reagent/worktrees/<id>`), and a `unit` (`{ id, title, scope, planDocPath }`).

**2. Rules section — add a new rule after the existing branch rule:**

After the rule "Do all git work on the branch passed in as `branch`…", add:

> - Work inside the `worktreePath` directory, not inside `repoPath`. The worktree is a separate checked-out copy linked to the same `.git` object store — edits and commits there are automatically visible to the reviewer via `git diff`.

**3. Procedure step 1 — replace the checkout instruction:**

Replace:

> 1. `cd` to `repoPath`. Create/switch to the `branch` you were given.

With:

> 1. Set up your working directory using the provided `worktreePath`:
>    - If the directory at `worktreePath` does not already contain a `.git` file (i.e. the worktree has not been added yet), run: `git -C <repoPath> worktree add <worktreePath> <branch>` — this creates the branch from the current HEAD and checks it out in the worktree. If the branch already exists (re-invocation after review FAIL), append `--checkout` or omit and let git handle it; use `git -C <repoPath> worktree add --checkout <worktreePath> <branch>` in that case.
>    - `cd` to `worktreePath`. All subsequent reads, edits, and git commands (except worktree management) run from here.
>    - Do NOT run `git checkout` in `repoPath` — that would disturb the shared working tree.

The exact wording should be clear and concise for the agent model. A simplified version that is equally correct:

> 1. Prepare your isolated working directory:
>    a. Check whether `worktreePath` already contains a `.git` file: `test -f <worktreePath>/.git`.
>    b. If it does NOT exist yet: `git -C <repoPath> worktree add <worktreePath> <branch>` (creates and checks out the branch in the worktree).
>    c. If it already exists (re-invocation): the worktree is already set up — just `cd` into it.
>    d. All subsequent file edits and `git` commands run from `worktreePath`, not `repoPath`.

**4. Procedure step 5 — git commit:**

No change needed to step 5. Commits made from within the worktree are visible to `git log` and `git diff` on the shared `.git`, so the reviewer can diff them without modification.

**5. Procedure step 6 — report_status:**

No change. The `branch` passed in is the same branch value used in `report_status`.

## Acceptance criteria

1. `agents/reagent-executor.md` mentions `worktreePath` in the inputs paragraph (line 8 area).
2. The Rules section contains a rule directing the executor to work inside `worktreePath`, not `repoPath`.
3. Procedure step 1 describes `git worktree add <worktreePath> <branch>` as the setup command, with a conditional for re-invocation (worktree already exists).
4. Procedure step 1 does NOT say `git checkout` in `repoPath`.
5. No other procedure steps are changed in substance.
6. No other files are modified.
